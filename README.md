### 🚥 2. 부하 테스트 시나리오

> k6 (ramping-arrival-rate) 사용

- [x] `GET /api/albums`
  - 읽기 부하 테스트

  - 쓰기 트래픽 부하 테스트
  - 새 앨범 생성 요청을 **500 req/s**까지 설정
- [ ] `PATCH /albums/:id`

### 📄 5. 성능 결과

#### `GET /albums` 성능 개선 (Redis 캐싱 적용 전/후 비교)

| 지표                             | 캐싱 전 (No Redis)                   | 캐싱 후 (Redis 적용)               | 변화                             |
| -------------------------------- | ------------------------------------ | ---------------------------------- | -------------------------------- |
| **처리량 (http_reqs)**           | 108,887 req / 135.5s → **804 req/s** | 103,095 req / 120s → **859 req/s** | **+ 약 6.9% ↑**                  |
| **평균 지연시간 (avg duration)** | **100.03 ms**                        | **81.67 ms**                       | **약 -18.4% ↓**                  |
| **중앙값 (median)**              | 1.05 ms                              | 1.10 ms                            | 거의 동일                        |
| **p90**                          | 2.78 ms                              | 2.24 ms                            | **개선**                         |
| **p95**                          | 3.72 ms                              | 2.76 ms                            | **약 -25.8% ↓**                  |
| **실패율 (http_req_failed)**     | 0%                                   | 0%                                 | 동일 (안정적)                    |
| **dropped_iterations**           | 78,613                               | 84,403                             | 둘 다 많음 (k6 VU 제한으로 발생) |

### 요약

```Redis 캐싱을 적용하자 DB I/O가 줄어들며
RPS가 소폭 상승하고, 평균·p95 지연시간이 눈에 띄게 감소했다.
특히 고지연 tail latency의 개선이 명확하게 나타났다.
```
